# Cloud Extension Manager

Open `/prototype/homestead?v=2&flow=extensions`, or add `&scenario=first` to start as a new Cloud user without a custom environment. This opt-in journey starts in Cloud with a compatible workflow and a large modal for browsing and selecting node packs over the real editor. Search names, publishers and descriptions, or switch between all packs, installed packs and available updates. Compact rows show descriptions, installed versions and pending selections. A checkbox includes each pack in the desired environment; installed packs start checked, and unchecking stages removal. Choose versions separately. Pages contain five packs by default; selections persist across page changes, filters and searches. Homestead V1–V3 journeys remain available without `flow=extensions`.

Accounts without a custom environment first see a compact introduction led by “Your nodes. Powerful Cloud GPUs.” A single cloud icon accompanies the value proposition, with supporting community/private-node copy. Billing is a quiet, icon-free line: only pay for GPU seconds while jobs run, plus environment storage. **Learn more** links to https://comfy.org/pricing; **Get started** continues to pack selection inside Cloud. No unverified speedup or universal compatibility claim is made. Accepting the intro is retained for the current unfinished session; existing-custom accounts skip it.

The existing-environment scenario includes KJNodes and Impact Pack updates. Use **Update** to stage the latest release, or choose another version; removing a pack is an explicit reviewed change and never deletes graph nodes. **Add your own** appears above the catalog. Add a GitHub repository URL, or select a local ZIP through drag-and-drop or the file picker. The prototype validates the ZIP filename and records metadata only; it never reads or uploads archive contents. Close and reopen the manager to retain selections within the current page session.

For admins, **Next** advances through **Node packs → Models & LoRAs → Environment Settings** within the modal. Cloud-matched workflow models and inherited environment models start selected. The source-backed sample catalog offers checkpoints, LoRAs and other weights; unmatched workflow files appear separately as models to supply. **Add your own models** supports local drag-and-drop or Browse, and Hugging Face or other HTTPS file links, with a saved filename and model folder. Imports stage metadata only and remain selected across navigation and simulated build/application. Local byte sizes enter the package estimate; link sizes remain unknown. Existing private environment dependencies are retained separately from the Cloud catalog. Updating an existing custom environment shows a destination picker, defaulting to the current environment and marking it Current. The list includes custom environments and revisions; Standard Cloud is excluded as an update target. Choosing another destination retains its existing dependencies and applies staged pack/model changes without switching the running workflow. Creating a new environment remains available; first-time setup without custom environments creates new. Environment Settings shows the Environment name field only when creating a new environment; updates preserve the selected environment’s name. GPU settings remain editable and the complete selection is reviewed. GPU rows use Platform catalog fields: label, VRAM and hourly price, with per-second billing shown. A **Recommended** tag marks the lowest-priced GPU whose memory covers the current workflow’s model sizes plus illustrative headroom (1.5× weights + 8 GB). Other environment models do not inflate this recommendation. Unknown workflow sizes, no detected models or estimates beyond the offered GPUs produce no tag and an explanation. Existing GPU choices remain editable and unchanged; first-time defaults use the same size estimate. The cost review shows only read-only environment package size and estimated monthly storage cost. Package sizing includes the runtime, selected node packs and dependencies, and selected models. Unknown sizes produce a partial estimate; missing rates remain unavailable. Prototype runtime/pack/model sizes, GPU options/prices and storage rates are illustrative fixtures, not live quotes.

**Build environment** closes the modal and opens a dismissible status side panel, returning focus to the workflow canvas. Keep editing and submitting Run jobs on the working revision. Reopen progress through the persistent status indicator. The product panel shows grouped Platform stages with pending/current/completed/failed states: confirming selections, preparing node packs, checking and packaging, copying models, creating the environment, and starting it. Build success alone is insufficient: candidate deployment readiness precedes **Environment is ready** and **Apply environment**. The working/source environment remains unchanged until explicit application. Raw job IDs, revision listings and shared-session debug output are not part of this panel. Readiness and its email preview never authorize a switch: explicitly choose **Apply environment**. Approval pauses new submissions for everyone on the shared target; accepted running and queued jobs finish on the old revision before it switches. Unrelated environments stay runnable. The canvas, unsaved inputs and outputs remain in place. When activation finishes, the progress panel closes and a brief native notification confirms the selected environment. The cloud/server icon immediately before Run lists available environments and marks the current selection; switching there preserves the open workflow and any pending build. Creating new preserves the source and selects the new environment only for the initiating workflow, including when another workflow is active at completion. This session-selection behavior is a demo default pending product decisions.

Use **Demo scenarios & inbox** to select an existing environment, first-time setup, or the M2 team-request preview. Controls can simulate preparation failure, hold accepted jobs, seed running/queued jobs, or finish the next job. The demo popup has an explicit close button and supports Escape and outside-click dismissal. Selecting a scenario or following an inbox action dismisses the popup before opening its destination. Failure retains selections and offers retry, edit, and copying repair context to local Codex/Claude. M2 previews all-admin requests, preselected review and requester availability after explicit application.

First-time setup stays entirely in Cloud: select packs, select additional models and LoRAs, review the new environment name, priced GPU options and calculated storage costs, prepare in the background, then explicitly approve using the new environment. Standard Cloud remains usable through preparation or failure. Applying the first custom environment changes only the initiating workflow and preserves Standard Cloud for other workflows. The manager then supports updates to that newly created environment. No paid-tier gate is introduced. After application, selected RMBG/Acme fixture nodes appear in editor search and the node library. Other packs are manifest simulations.

All preparation, jobs, roles, notifications and environment changes are local simulations. There is no GPU execution, billing, upload, repository fetch, real email, production mutation or integrated repair. Refresh resets the demo; persistence across refresh or tab closure is not promised.

Members use a two-step request flow: **Node packs → Models & LoRAs → Send request**. The last enabled selection step includes an expandable summary of pack/model changes and an optional note to admins, retained when the modal is reopened. Sending closes the modal and shows only a brief “Request emailed to workspace admins” notification; it does not open the side panel. The admin notification opens **Environment Settings** with the requested packs/models and note prefilled; only admins review GPU, destination and costs before building and applying.

Enterprise controls determine the selection steps: enable adding nodes for the pack step, enable adding models for the model/LoRA step, or enable both for the full two-step request. With both disabled, Extensions is disabled with a hover/focus tooltip explaining the admin policy. Existing environment dependencies are retained for disabled categories. In **Demo scenarios & inbox → Team request**, the two Enterprise controls toggles simulate these configurations. Model/LoRA selection uses the full modal width; an expandable request summary preserves selection space in narrow windows.

The single Extensions entry is the existing blocks icon to the right of Run on the canvas action bar. The duplicate top-bar entry is removed. This icon opens the first-time introduction or current selection flow and retains enterprise policy disabling/tooltips. Closing or escaping the modal returns focus to the canvas icon. The top strip retains environment context, preparation status and demo controls.

Failure recovery prioritizes **Copy error for local agent** as a full-width primary button, with copy/check feedback and local Codex/Claude instructions. **Retry** and **Edit selections** are equal secondary actions with refresh/pencil icons. Error details are expandable. Copy includes the diagnostic error, preserved environment revision, requested configuration and repair instructions; it does not invoke an agent.
